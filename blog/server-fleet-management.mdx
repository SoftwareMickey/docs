Last time, we introduced Beaver CLI and promised that connecting your own servers was coming next. It's here — and it turned out to be about more than just registering a machine. A server you own can play different roles in your deployment pipeline, and Beaver CLI now knows the difference.

## `beaver connect`: register any server, any role

Running `connect` on a machine no longer just adds it to your workspace — it inspects the machine first. Operating system and architecture, Git and Docker, whether the Docker daemon is actually reachable by the current user, available disk and memory, and what kind of machine this even is: a laptop, a cloud VPS, bare metal, or a CI runner.

That inspection matters because not every server should do the same job. A laptop is often a perfectly good place to build Docker images — but it sleeps, changes networks, and loses power, which makes it a poor place to host production traffic. A VPS or bare-metal box can usually do both safely. So instead of asking you to guess, `connect` only offers the roles a machine actually qualifies for:

- **Builder** — clones repositories, builds images, nothing else.
- **Host** — pulls images and runs containers, nothing else.
- **Builder + Host** — both, on a single machine.

If a machine can host but only with caveats (a laptop, say, or an ephemeral CI runner), Beaver CLI says so explicitly and asks you to confirm before proceeding — never a silent assumption.

```bash
beaver connect
```

## Managing your fleet

Once a server is enrolled, `server` is how you manage it — list what's connected, and update, rename, or remove entries without ever touching the machine itself:

```bash
beaver server --list
beaver server update <machine-id> --role host
beaver server rename <machine-id> prod-eu-west
beaver server remove <machine-id>
```

`update` also accepts `--labels`, for arbitrary key/value tags like `environment=production` — useful once a fleet grows past a handful of machines. And if you don't have a machine ID memorized, running `update` or `remove` with none pulls up an interactive picker: arrow keys to move, type to filter, Enter to confirm.

## Keeping the CLI itself current

Beaver CLI can now update itself:

```bash
beaver update
```

It checks the latest release, downloads and verifies the right build for your platform, and replaces itself in place — no separate download step, no reinstalling by hand.

## Still the same philosophy

None of this changes what Beaver CLI fundamentally is. Your servers are still yours — Beaver only orchestrates what runs where, based on what each machine actually qualifies for.
