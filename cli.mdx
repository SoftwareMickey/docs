VectorIHub gives you a command-line interface — `beaver` — for interacting with your VectorIHub account and infrastructure from a terminal or an automated environment like CI, instead of the [dashboard](https://vectorihub.com).

<Info>
  The current CLI covers authentication, machine enrollment, project preparation, deployment, live inspection, recovery, fleet operations, security, billing, integrations, and AI-assisted workflows.
</Info>

## Installing the CLI

<Info>
  New to Beaver? [Install Beaver CLI on Linux](/installation) walks through connecting a Linux machine, while [Windows installation](/installation-windows) covers installing the CLI on Windows.
</Info>

<Tabs>
  <Tab title="macOS / Linux">
    Install with the install script — it detects your OS and architecture, downloads the matching release, verifies its checksum, and installs `beaver` to `/usr/local/bin`:

    <CodeGroup>
    ```bash Install script
    curl -fsSL https://cli.vectorihub.com/install.sh | sh
    ```
    </CodeGroup>

    <Tip>
      Set `INSTALL_DIR` to install somewhere other than `/usr/local/bin`, or `VERSION` to install a specific release instead of the latest:

      ```bash
      curl -fsSL https://cli.vectorihub.com/install.sh | INSTALL_DIR=$HOME/.local/bin VERSION=0.1.1 sh
      ```
    </Tip>
  </Tab>
  <Tab title="Windows">
    Install with PowerShell. The installer detects x86, x64, or ARM64, downloads the matching ZIP, verifies its checksum, installs `beaver.exe` in your user profile, and adds it to your `PATH`:

    ```powershell
    irm https://cli.vectorihub.com/install.ps1 | iex
    ```

    Run this in PowerShell, not Command Prompt. From Command Prompt, use `powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://cli.vectorihub.com/install.ps1 | iex"`.

    See [Install Beaver CLI on Windows](/installation-windows) for verification, custom installation directories, and troubleshooting.
  </Tab>
</Tabs>

### Verifying the installation

```bash
beaver version
```

```txt Example output
🐹 VectorIHub CLI v0.1.3 (a1b2c3d)
```

<Note>
  The commit hash only appears on release builds — it's injected via `-ldflags` at build time. A binary built locally with `go build` just shows the version.
</Note>

## Updating the CLI

Run the built-in update command — it checks the latest release, downloads the matching archive for your OS and architecture, verifies its checksum against `checksums.txt`, and atomically replaces the running binary in place:

```bash
beaver update
```

```txt Example output
Checking for updates...
Updating beaver v0.1.2 -> v0.1.3...
Downloading beaver_0.1.3_linux_amd64.tar.gz...
Verifying checksum...

────────────────────────────────────────────

✓ beaver updated to v0.1.3 🦫

  Previous   v0.1.2
  Current    v0.1.3

Restart `beaver` to start using the new version.
```

<Tip>
  Pass `--version` to install a specific release instead of the latest:

  ```bash
  beaver update --version 0.1.1
  ```
</Tip>

`beaver update` works the same way on macOS, Linux, and Windows, whether you're inside the interactive shell or running it directly from your terminal. If you're already on the requested version, it tells you so and exits without downloading anything.

## Using the CLI

Running `beaver` with no arguments deploys the current project, matching the direct workflow used by modern deployment CLIs. Open the optional interactive shell with `beaver shell`:

```bash
beaver shell
```

```txt Interactive shell
🦫 beaver v0.1.3 (a1b2c3d)

Build once. Deploy anywhere.

The deployment control plane for infrastructure you own.

Connected:
  Account     yourname
  Workspace   yourname's workspace

Quick start:

  login      Authenticate your Beaver account
  logout     Sign out and clear your local session
  connect    Enroll this server with Beaver
  doctor     Check whether this machine is ready for Beaver
  server     Manage enrolled servers — try `server --list`
  update     Update the CLI to the latest release
  github     List connected GitHub accounts
  help       Show available commands
  exit       Quit the CLI

Ready.

beaver ▸
```

If you haven't logged in yet, the banner shows `Not connected — type login to authenticate` instead — the shell never blocks on login, so it always opens instantly even against an unreachable backend.

At the `beaver ▸` prompt, type any command listed under the command reference below and press Enter. A few behaviors worth knowing:

- **Command history.** On a real terminal, `beaver shell` remembers what you've typed — press <kbd>↑</kbd>/<kbd>↓</kbd> to recall previous commands, including across separate sessions. Piped or non-interactive input transparently falls back to plain line reads instead.
- <kbd>Ctrl</kbd>+<kbd>C</kbd> clears whatever you've typed on the current line and reprompts — it does **not** exit the shell.
- <kbd>Ctrl</kbd>+<kbd>D</kbd> (EOF), or typing `exit`/`quit`, ends the session:

  ```txt
  ✓ Session closed.

  Beaver will be ready when you are.
  ```

### Running commands directly

All public commands work directly from your OS shell. The interactive shell is optional:

```bash
beaver doctor
beaver github
beaver server --list
beaver update
beaver version
beaver login
beaver connect
```

<Note>
  Use `beaver --help` to discover commands, `beaver help <command>` or `beaver <command> --help` for detailed usage, `beaver --cwd <path>` to run from another project directory, and `beaver --no-color` for plain output.
</Note>

## Current command reference

The full, exhaustive reference for every command and flag lives on its own page, linked from
the sidebar under **CLI**. This section is a map of what's where, not a restatement of it —
run `beaver <command> --help` for the exact flags shipped in your version, or open a page
below for the full walkthrough (purpose, every flag, consequences, and examples).

### Daily project workflow

[`init`](/cli/init) prepares the current directory; [`validate`](/cli/validate) checks it
without deploying; [`config`](/cli/config) authors and inspects `.beaver/config.yml` in
depth; [`plan`](/cli/plan) previews what a deploy of one container would do.
[`deploy`](/cli/deploy) builds and ships the current directory or a connected GitHub repo.
After a deploy, use [`inspect`](/cli/inspect) for a quick summary,
[`observe`](/cli/observe) for logs/traffic/metrics together,
[`status`](/cli/status) for declared-vs-live comparison, [`diff`](/cli/diff) to compare two
releases, and [`recover`](/cli/recover) to diagnose or explicitly restart/roll back.
[`state`](/cli/state) and [`reconcile`](/cli/reconcile) cover the saved-vs-running
comparison and catch-up story in more depth.

### Containers, deployments, and Compose

[`containers`](/cli/containers) lists everything deployed; [`container`](/cli/container)
inspects, logs, redeploys, restarts, rolls back, or deletes **one** container.
[`deployment`](/cli/deployment) is the history/control surface for individual deployment
attempts, by ID. [`compose`](/cli/compose) detects, deploys, and operates multi-service
Compose stacks. [`promote`](/cli/promote) moves an already-built image to another
environment without rebuilding.

### Projects, environments, and domains

[`project`](/cli/project), [`environment`](/cli/environment), and [`domain`](/cli/domain)
cover project grouping, environment/branch mapping, and custom domains.
[`route`](/cli/route) inspects a domain's live DNS/TLS/backend health in one place.

### Fleet and infrastructure

[`doctor`](/cli/doctor) checks local prerequisites; [`connect`](/cli/connect) enrolls a
machine as Builder, Host, or Builder + Host; [`server`](/cli/server) manages enrolled
machines without touching the physical machine; [`agent`](/cli/agent) manages the local
background service. [`machine`](/cli/machine) is fleet-wide visibility and maintenance —
metrics, events, alerts, security posture, cleanup, reboot, and autopilot policy.
[`health`](/cli/health) sets a service's HTTP health-check path.
[`mystic`](/cli/mystic) and [`preflight`](/cli/preflight) are build-acceleration and
pre-deploy diagnostics.

### Cloud, firewall, scaling, and Edge

[`cloud`](/cli/cloud) groups enrolled machines into a pool with shared networking, capacity,
and workload placement. [`firewall`](/cli/firewall) manages per-deployment WAF/rate-limit/IP
policy; [`edge`](/cli/edge) fronts an external service behind a domain, with its own firewall
mirror. [`scaling`](/cli/scaling) manages replica policy and staged/canary rollouts;
[`autoscale`](/cli/autoscale) is the quick one-command form of the common case.
[`service`](/cli/service) provisions and operates managed stateful dependencies (databases,
caches) — including clusters and backup destinations — distinct from your own application
containers.

### Account, billing, integrations, and AI

[`login`](/cli/login)/[`logout`](/cli/logout)/[`whoami`](/cli/whoami) manage your session.
[`account`](/cli/account), [`workspace`](/cli/workspace), [`billing`](/cli/billing),
[`plans`](/cli/plans), and [`coupon`](/cli/coupon) cover profile, workspace, and payment.
[`github`](/cli/github) and [`integrations`](/cli/integrations) manage connected accounts.
[`ai`](/cli/ai) connects AI provider API keys (machine-local via `ai connect`, or a
Beaver-cloud-stored fallback via `ai provider add`) for use by [`alie`](/cli/alie), Beaver's
infrastructure assistant — which also covers approvals, autopilot, spend caps, and
workspace-wide knowledge/goals/policies. [`skills`](/cli/skills) publishes reusable skill
packages Alie can use.

<Note>
  Treat every credential here — API keys, tokens, the Alie API key shown once at
  creation — like a password.
</Note>

## Troubleshooting

| Symptom | What to do |
| --- | --- |
| Not logged in | Run `beaver login`, then `beaver whoami`. |
| `connect` stops | Run `beaver doctor --verbose`; fix the first failed check. |
| Enrolled machine unavailable | Run `beaver agent status` and `beaver agent logs`; verify network and Docker. |
| Deployment waits or fails | Run `beaver deployment status <id>` and `beaver deployment logs <id>`; check Dockerfile, context, machines, registry, and variables. |
| Domain verification fails | Check DNS, wait for propagation, then rerun `beaver domain verify <id>`. |
| CI cannot run an interactive command | Supply IDs and flags, use `--yes`, and select `--json`/`--quiet`. |
| Flag is rejected | Run `beaver <command> --help`; update if installed help disagrees. |

When reporting an issue, include `beaver version`, the exact command, the first error, and relevant doctor output. Redact tokens, passwords, private keys, and secret values.

### Utilities

```bash
beaver completion bash|zsh|fish|powershell
beaver history
beaver version
```

Use `completion <bash|zsh|fish|powershell>` to generate shell completion; `history` accepts `--since <duration>` and `--project <project>`; `version` verifies an installation or update. The `admin` namespace is reserved for administrative workflows and is not part of the end-user command surface.
