VectorIHub gives you a command-line interface — `beaver` — for interacting with your VectorIHub account and infrastructure from a terminal or an automated environment like CI, instead of the [dashboard](https://vectorihub.com).

<Info>
  The current CLI covers authentication, machine enrollment, project preparation, deployment, live inspection, recovery, fleet operations, security, billing, integrations, and AI-assisted workflows.
</Info>

## Installing the CLI

<Info>
  New to Beaver? [Install Beaver CLI on Linux](/installation) walks through connecting a Linux machine, while [Windows installation](/installation-windows) covers installing the CLI on Windows.
</Info>

<Tabs>
  <Tab title="macOS / Linux">
    Install with the install script — it detects your OS and architecture, downloads the matching release, verifies its checksum, and installs `beaver` to `/usr/local/bin`:

    <CodeGroup>
    ```bash Install script
    curl -fsSL https://cli.vectorihub.com/install.sh | sh
    ```
    </CodeGroup>

    <Tip>
      Set `INSTALL_DIR` to install somewhere other than `/usr/local/bin`, or `VERSION` to install a specific release instead of the latest:

      ```bash
      curl -fsSL https://cli.vectorihub.com/install.sh | INSTALL_DIR=$HOME/.local/bin VERSION=0.1.1 sh
      ```
    </Tip>
  </Tab>
  <Tab title="Windows">
    Install with PowerShell. The installer detects x86, x64, or ARM64, downloads the matching ZIP, verifies its checksum, installs `beaver.exe` in your user profile, and adds it to your `PATH`:

    ```powershell
    irm https://cli.vectorihub.com/install.ps1 | iex
    ```

    Run this in PowerShell, not Command Prompt. From Command Prompt, use `powershell -NoProfile -ExecutionPolicy Bypass -Command "irm https://cli.vectorihub.com/install.ps1 | iex"`.

    See [Install Beaver CLI on Windows](/installation-windows) for verification, custom installation directories, and troubleshooting.
  </Tab>
</Tabs>

### Verifying the installation

```bash
beaver version
```

```txt Example output
🐹 VectorIHub CLI v0.1.3 (a1b2c3d)
```

<Note>
  The commit hash only appears on release builds — it's injected via `-ldflags` at build time. A binary built locally with `go build` just shows the version.
</Note>

## Updating the CLI

Run the built-in update command — it checks the latest release, downloads the matching archive for your OS and architecture, verifies its checksum against `checksums.txt`, and atomically replaces the running binary in place:

```bash
beaver update
```

```txt Example output
Checking for updates...
Updating beaver v0.1.2 -> v0.1.3...
Downloading beaver_0.1.3_linux_amd64.tar.gz...
Verifying checksum...

────────────────────────────────────────────

✓ beaver updated to v0.1.3 🦫

  Previous   v0.1.2
  Current    v0.1.3

Restart `beaver` to start using the new version.
```

<Tip>
  Pass `--version` to install a specific release instead of the latest:

  ```bash
  beaver update --version 0.1.1
  ```
</Tip>

`beaver update` works the same way on macOS, Linux, and Windows, whether you're inside the interactive shell or running it directly from your terminal. If you're already on the requested version, it tells you so and exits without downloading anything.

## Using the CLI

Running `beaver` with no arguments deploys the current project, matching the direct workflow used by modern deployment CLIs. Open the optional interactive shell with `beaver shell`:

```bash
beaver shell
```

```txt Interactive shell
🦫 beaver v0.1.3 (a1b2c3d)

Build once. Deploy anywhere.

The deployment control plane for infrastructure you own.

Connected:
  Account     yourname
  Workspace   yourname's workspace

Quick start:

  login      Authenticate your Beaver account
  logout     Sign out and clear your local session
  connect    Enroll this server with Beaver
  doctor     Check whether this machine is ready for Beaver
  server     Manage enrolled servers — try `server --list`
  update     Update the CLI to the latest release
  github     List connected GitHub accounts
  help       Show available commands
  exit       Quit the CLI

Ready.

beaver ▸
```

If you haven't logged in yet, the banner shows `Not connected — type login to authenticate` instead — the shell never blocks on login, so it always opens instantly even against an unreachable backend.

At the `beaver ▸` prompt, type any command listed under the command reference below and press Enter. A few behaviors worth knowing:

- **Command history.** On a real terminal, `beaver shell` remembers what you've typed — press <kbd>↑</kbd>/<kbd>↓</kbd> to recall previous commands, including across separate sessions. Piped or non-interactive input transparently falls back to plain line reads instead.
- <kbd>Ctrl</kbd>+<kbd>C</kbd> clears whatever you've typed on the current line and reprompts — it does **not** exit the shell.
- <kbd>Ctrl</kbd>+<kbd>D</kbd> (EOF), or typing `exit`/`quit`, ends the session:

  ```txt
  ✓ Session closed.

  Beaver will be ready when you are.
  ```

### Running commands directly

All public commands work directly from your OS shell. The interactive shell is optional:

```bash
beaver doctor
beaver github
beaver server --list
beaver update
beaver version
beaver login
beaver connect
```

<Note>
  Use `beaver --help` to discover commands, `beaver help <command>` or `beaver <command> --help` for detailed usage, `beaver --cwd <path>` to run from another project directory, and `beaver --no-color` for plain output.
</Note>

## Current command reference

The command surface has expanded beyond the original setup-only workflow. The following reference reflects the current CLI. Run `beaver <command> --help` for the exact flags shipped in your version.

### Daily project workflow

```bash
beaver init [--guided|--propose]
beaver validate
beaver contract show
beaver plan [--env <environment>] [--json]
beaver deploy [--single|--git] [--dockerfile <path>]
beaver inspect [service]
beaver observe [service] [--logs|--traffic|--metrics <name>] [--follow]
beaver status [--env <environment>] [--explain]
beaver recover [service] [--explain|--restart|--rollback]
beaver diff [service] [release-a] [release-b]
```

Use `init` to prepare the current directory, `validate` to check it without deploying, `contract show` to view normalized configuration, and `plan` to preview a deployment. `deploy` uses the current directory by default; its non-interactive flags include `--project-id`, `--repo`, `--branch`, `--commit`, `--builder-id`, `--host-id`, `--container-name`, `--container-port`, `--host-port`, `--docker-user`, `--image`, `--deployment-path`, `--env-file`, repeatable `--env-var KEY=value`, `--env`, `--framework`, `--dry-run`, `--logs`, `--wait`, `--timeout`, `--output`, `--json`, `--quiet`, and `--yes`.

After a successful deploy, use `inspect` for a summary, `observe` for logs/traffic/metrics, `status` for declared-versus-live comparison, `diff` for release comparison, and `recover` for diagnosis or an explicitly requested restart/rollback. Deployment IDs can be inspected with `beaver deployment`.

### Containers, deployments, and Compose

```bash
beaver containers
beaver container <name> inspect|logs|history|redeploy|restart|rollback|delete
beaver deployment list <container>
beaver deployment show|status|logs|watch|retry|cancel <deployment-id>
beaver compose detect
beaver compose deploy
beaver compose stacks
beaver compose stack show|networks|volumes|delete <stack-id>
beaver compose release show|watch|rollback|retry|cancel <release-id>
```

Container commands inspect, log, redeploy, restart, roll back, or delete one deployed container. Deployment commands provide history, status, request logs, live progress, retry, and cancellation by ID. Compose commands detect resources, deploy a stack, and operate its stacks and releases. Confirm destructive actions; use `--yes` where supported.

### Projects, environments, and domains

```bash
beaver project list|show <project-id>|create|delete <project-id>
beaver environment list|create|delete <environment-id>
beaver environment vars list|pull|push|diff [service]
beaver domain list|add|verify <domain-id>|certificate <domain-id>|remove <domain-id>
```

Projects group applications, containers, and environments. Use `--env` with `plan`, `deploy`, and `status`. Review environment-variable changes before pushing and never commit secrets. Domain verification requires DNS propagation; `certificate` provisions or reprovisions TLS.

### Fleet and local machine operations

```bash
beaver doctor [--verbose]
beaver connect [--verbose]
beaver server --list
beaver server update [machine-id] [--name <name>] [--role builder|host|builder-host] [--labels key=value,...] [--yes]
beaver server rename <machine-id> <new-name>
beaver server remove [machine-id] [--yes]
beaver agent install|start|stop|status|logs
beaver git --auth
beaver docker --auth
```

`doctor` checks local prerequisites and offers targeted repairs. `connect` enrolls the current Linux machine as a Builder, Host, or Builder + Host. `server` manages enrolled machines; it does not delete the physical machine. `agent` manages the local Beaver background service. Git and Docker are focused authentication checks.

Fleet visibility and maintenance:

```bash
beaver machine list|overview|show|live|services|docker|events|metrics|trends|alerts|alert-rules|approvals|security|exposure|log-inventory <machine-id>
beaver machine fleet-overview|fleet-drift|fleet-capacity|groups
beaver machine group-policy <group-id>
beaver machine policy <machine-id>
beaver machine policy set <machine-id>
beaver machine reboot-impact|reboot|package-update|cleanup-plan|cleanup|maintenance-windows|maintenance-runs <machine-id>
beaver machine restart-service <machine-id> --service <service-name>
beaver machine monitoring <machine-id>
```

Use `reboot-impact` and `cleanup-plan` before mutating actions. Metrics support the documented `--window`/`--metric` options; event views may support `--limit`, `--category`, and `--severity`.

### Firewall, scaling, and Edge

```bash
beaver firewall overview|policy|rules|revisions|events|bans|waf|intel <deployment-id>
beaver firewall rule add|update|delete <deployment-id> [rule-id]
beaver firewall rollback <deployment-id> <revision-id>
beaver firewall preset apply <deployment-id> --preset <name>
beaver firewall ban <deployment-id> --ip <ip> --reason <reason>
beaver firewall unban <deployment-id> <ip> [--yes]
beaver firewall login-protect <deployment-id> --path <path>
beaver firewall lockdown|unlock <deployment-id>
beaver firewall visibility <deployment-id> --public|--private
```

Firewall rule types are `ip`, `path`, `method`, `query`, and `header`; actions are `allow`, `block`, `rate-limit`, and `challenge`. `lockdown` blocks all traffic until `unlock`. A visibility or WAF change may require redeployment. Use `--service` for one Compose service.

```bash
beaver scaling policy|set|replicas|events|rollouts|deploy-set <container>
beaver scaling cutover|discard <container> <rollout-id>
beaver scaling canary <container>
beaver scaling canary-status <rollout-id>
beaver edge apps
beaver edge app add|show|update|remove|verify|rotate-secret|origin-protection|origin-protection-recheck [connected-app-id]
beaver edge backends <connected-app-id>
beaver edge backend add|remove|import <connected-app-id> [backend-id]
beaver edge detected-services <machine-id>
beaver edge logs|traffic|speed <connected-app-id>
beaver edge firewall policy|rules|revisions <connected-app-id>
beaver edge firewall rule add|update|delete <connected-app-id> [rule-id]
beaver edge firewall rollback <connected-app-id> <revision-id>
beaver edge firewall preset apply|ban|unban|lockdown|unlock <connected-app-id>
```

Scaling manages replica policies and staged or gradual traffic changes. Edge Connected Apps front existing external services; verify the domain and origin before making one public. Use each command's help for operation-specific fields.

### Account, billing, integrations, and AI

```bash
beaver account profile show|update
beaver account mfa setup|verify|disable
beaver account feedback
beaver workspace show|recreate
beaver plans
beaver billing subscription|checkout|cancel|downgrade-hobby|payments
beaver github accounts|install|branches
beaver integrations status
beaver integrations remove <integration-id>
beaver ai connect [provider]
beaver ai providers
beaver ai models
beaver ai provider add|test|update|remove [provider-id]
```

These commands manage profile/MFA, workspace recovery, plans and hosted checkout, payments, GitHub/integrations, and AI provider credentials. Treat credentials like passwords.

### Alie

```bash
beaver alie
beaver alie --resume [session-name-or-id]
beaver alie sessions|session|model|usage|compact|fork <session>
beaver alie status|model-profile|knowledge|runbooks|goals|policies|autopilot
beaver alie approvals|approve|reject|audit <approval-id>
beaver alie approval-policies|approval-policy set
beaver alie api-keys|create|revoke <key-id>
beaver alie spend-cap|spend-cap set

```

Alie explains infrastructure findings and can propose actions. Approval prompts and workspace policies determine whether a proposed action may proceed; review pending approvals and the audit view.

## Troubleshooting

| Symptom | What to do |
| --- | --- |
| Not logged in | Run `beaver login`, then `beaver whoami`. |
| `connect` stops | Run `beaver doctor --verbose`; fix the first failed check. |
| Enrolled machine unavailable | Run `beaver agent status` and `beaver agent logs`; verify network and Docker. |
| Deployment waits or fails | Run `beaver deployment status <id>` and `beaver deployment logs <id>`; check Dockerfile, context, machines, registry, and variables. |
| Domain verification fails | Check DNS, wait for propagation, then rerun `beaver domain verify <id>`. |
| CI cannot run an interactive command | Supply IDs and flags, use `--yes`, and select `--json`/`--quiet`. |
| Flag is rejected | Run `beaver <command> --help`; update if installed help disagrees. |

When reporting an issue, include `beaver version`, the exact command, the first error, and relevant doctor output. Redact tokens, passwords, private keys, and secret values.

### Utilities

```bash
beaver completion bash|zsh|fish|powershell
beaver history
beaver version
```

Use `completion <bash|zsh|fish|powershell>` to generate shell completion; `history` accepts `--since <duration>` and `--project <project>`; `version` verifies an installation or update. The `admin` namespace is reserved for administrative workflows and is not part of the end-user command surface.
