A `beaver` command exits **`0`** on success and **non-zero** on failure, so a script can use `&&`, `||` and `set -e`. Most failures exit `1`. A few commands use more specific codes so a script can branch.

Read a status together with the command that produced it: `3` and `4` mean different things under `beaver config` and under `beaver github install`. The same table is printed offline by `beaver help exit-status`.

The *reason* for a failure is not the status. Every failure carries a stable **code** — `error.code` in `--json` output — and each code has its own page in the [error code reference](/reference/errors). Branch on the code, not on the status or the message text.

## Waiting and timeouts

`--wait` blocks until a deployment or other operation reaches a final state; `--timeout` (default `5m`) bounds the wait. If the timeout passes the command exits non-zero, but **the operation itself is not cancelled** — check it with `beaver deployment status` instead of assuming it failed. See [Shared flags](/cli/shared-flags).

## Output formats

| Flag | Output |
| --- | --- |
| *(none)* | A human-readable table or report. Colour only on a terminal; `NO_COLOR` or `--no-color` turns it off |
| `--json` | One JSON document on standard output, and nothing else — safe to pipe to `jq`. Same as `--output json` |
| `--output yaml` | The same document as YAML |
| `--quiet` | Suppresses status lines (`Rebooting…`, `✓ Done`) and still prints the data, in whatever `--output` selects |
| `--yes` | Skips a confirmation prompt. It never changes what the command does |

In a table-mode failure the report goes to **standard error**; in JSON or YAML mode the error is the document on standard output.

### Shape of JSON output

`beaver config` commands wrap their result in an envelope:

```json
{ "ok": true, "data": { "valid": true, "errors": null }, "error": null }
```

Other commands print their data directly (`beaver whoami --json` prints `{ "logged_in": false }` when signed out). Treat the **field names of a command's own data as the contract you can test against today**; there is no published promise that every command keeps the same envelope.

Every failure in JSON mode is one document of this shape, whatever the command:

```json
{
  "ok": false,
  "error": {
    "code": "INVALID_REQUEST",
    "message": "unknown flag: --nope",
    "changed": false,
    "conditions": [],
    "repairs": []
  }
}
```

`code` is a stable, upper-case name (`INVALID_REQUEST`, `OPERATION_FAILED`, `MFA_REQUIRED`, `PLAN_LIMIT_REACHED`, `PRODUCTION_RESTRICTED` …); branch on it rather than on `message`. `changed` says whether anything was modified before the failure. `conditions` and `repairs` list what was wrong and what to do about it.

## In CI

```bash
beaver deploy --cloud paperclip-prod --wait --timeout 10m --json > result.json
code=$?
if [ "$code" -eq 77 ]; then echo "this workspace requires 2-step verification"; fi
exit "$code"
```
