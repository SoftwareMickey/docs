**The service's machine is not connected**

Beaver cannot reach the machine the service runs on, so it cannot tell what state the container is in. Retry when the machine is online; a detach may be recorded now with revoke_later and finished when it reconnects.

| | |
| --- | --- |
| Code | `SERVICE_MACHINE_UNREACHABLE` |
| Kind | Temporary |
| HTTP status | `503` |
| CLI exit status | `1` |

## What to do

Nothing was changed — the machine is asked before anything is dispatched. `delete` and `delete-volume` wait for the machine (`--wait-for-machine`, 60s by default) and only ask you to confirm once it is connected, so a refusal here means you were never asked and nothing was destroyed. Otherwise wait until the machine is online and run the command again; for a detach you cannot wait for, `--revoke-later` records it now — the application's credential may still work until the machine is back. See [A service's container went missing](/operate/service-container-missing#the-machine-is-not-connected).

## What the response contains

Every failure — in the table output, `--json`, `--yaml` and the API — carries the same fields: `code`, `message`, `changed` (whether anything was altered), `conditions` (each requirement checked, with `status`, `detail` and a `repair`), `repairs`, a `retry` command and a `request_id`. Branch on `error.code`, never on the message text.

```json
{
  "ok": false,
  "error": {
    "code": "SERVICE_MACHINE_UNREACHABLE",
    "message": "The service's machine is not connected",
    "changed": false,
    "conditions": [],
    "repairs": [],
    "request_id": "req_…",
    "error": "The service's machine is not connected"
  }
}
```

Look it up offline with `beaver help SERVICE_MACHINE_UNREACHABLE`. See [Exit codes and output formats](/reference/exit-codes-and-output) for what a script can rely on.
