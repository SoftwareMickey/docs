When a deploy goes wrong, or you want to move a build between environments, several
different commands apply — and which one you reach for matters, since they restore
different things.

```bash
beaver recover
beaver promote production
```

## Start read-only

`beaver recover` on its own diagnoses without changing anything — always start there. Add
`--explain` for the reasoning, `--rollback` or `--restart` once you've decided what to do
about it.

## Two things both called "rollback"

**Release rollback** restores a previous deployed build of your application. **Configuration
rollback** (see [State and drift](/concepts/state-and-drift)) restores a previous saved
configuration. These are different actions that happen to share a word — check which one a
command acts on before running it.

## What promotion actually moves

**Promotion** moves a built artifact from one environment to another — staging to
production, say — without rebuilding it. Only the artifact moves; environment-specific
settings like variables stay environment-specific.

## Whether data is affected

That depends entirely on what you're rolling back or recovering. A release rollback doesn't
touch attached services' data at all. A configuration rollback that changes a volume
declaration can. Check the specific action's own documented consequences rather than
assuming "rollback" is always purely code-level.
