A **project** groups everything for one application: its environments, deployments, and any
services attached to it. It's the unit most other concepts nest inside — see [How Beaver
fits together](/concepts/how-beaver-fits-together) for the full tree.

```bash
beaver project list
beaver project show <project-id>
```

## Why this matters

Once you have more than one application, keeping their environments and services from
bleeding into each other matters — a `staging` environment in one project has nothing to do
with a `staging` environment in another. The project boundary is what keeps that clean, and
it's usually the first thing you create.

## A project belongs to one workspace

Every project lives in exactly one [workspace](/concepts/workspaces-and-teams) — the one that was
active when it was created. Switching workspace switches the projects you see: the dashboard,
`beaver project list` and every other project command show only the active workspace's
projects. A project from another workspace — even one you own — is reported as not found
there, never shown or changed.

Members of a team workspace all see its projects; what each of them may do with one depends
on their role. A team workspace can't be deleted while it still has projects: delete them
first, so nothing is left running in a workspace no one can reach.

## What you can see and control

A project can hold multiple deployable applications (containers) under one shared set of
environments. You can link it to a local directory or a connected GitHub repository — either
way, `beaver project show` gives you the ID you'll reference everywhere else.

## Deleting a project is permanent

<Warning>
  This is a hard delete, not an archive. Every container and deployment inside the project
  is removed along with their Docker networks, and none of it can be recovered afterward.
  Containers keep running on their host machines until Beaver's own cleanup catches up — the
  delete itself doesn't stop them first.
</Warning>
