Inside one service (say, a Postgres instance), you can have multiple isolated **resources** —
one per application that uses it, so each application's data stays isolated even when
sharing the underlying service. What that resource is called depends on the service type: a
database for Postgres/MySQL/MongoDB, a key space for Redis, a messaging area for RabbitMQ, a
bucket for MinIO, an index for Meilisearch, a subject prefix for NATS, a topic prefix for
Kafka. This page uses "database" as the running example — everything on it applies the same
way to every other resource kind.

```bash
beaver service reveal paperclip-db
```

## Why share one service instead of running several

Two applications both needing Postgres doesn't mean you need two separate service instances
to manage, back up, and pay for. A private resource per application gets you isolation
without the operational overhead of running more services than you need — and connecting a
new application creates one automatically, with no separate provisioning step.

## Private by default, shared on purpose

Connecting a new application always gives it a brand-new, private resource unless you say
otherwise — nothing else can read or write it. If two applications genuinely need to work on
the same data (an API and its background worker, say), you connect the second one to the
first's existing resource and confirm the sharing explicitly (`beaver service attach
--database <name> --shared`). Either way, every connected application gets its **own**
credential — two applications sharing a resource never share a login.

## What you can see and control

Connection details (host, port, resource name) are shown by default; the actual credential
value stays hidden until you explicitly reveal it, which asks for confirmation first.
Rotating a credential issues a new value and invalidates the old one — any connection still
using the old value stops working and needs to reconnect with the new one.

## Detach revokes access, never data

Detaching an application from a service ends **that application's own** access: its injected
connection variables are removed, and its individual credential stops working. The resource
and its data are untouched — including any other application still connected to the same
resource. A resource with nothing left connected to it is reported as unused, but is never
deleted as a side effect of a detach; deleting it is always its own separate, confirmed
command (`beaver service database delete`).

<Warning>
  Rotating a credential is not reversible — the old value cannot be recovered once replaced.
  Update every place that used it before, or immediately after, rotating.
</Warning>
