A Beaver Cloud places **new** work; it does **not** move existing work when a machine goes offline. Taking a machine out of service is therefore something you do on purpose.
All of the steps are CLI commands.

<Note>
Two words are easy to mix up. **Cordon** (`beaver cloud machines cordon`) stops *new* work landing on a machine and leaves everything running; **drain** (`beaver cloud machines drain`)
cordons it **and** moves what runs there to other machines, keeping each old copy until its replacement is healthy. The older `beaver cloud drain` marks a machine as *leaving* the
cloud (a membership state) — to just stop new work, use `cordon`. See [Member vs compute](/infrastructure/member-vs-compute).
</Note>

<Warning>
There is no automatic failover. If a machine is lost, what ran on it stays down until you redeploy or evacuate it. Plan with `impact` **before** it happens.
</Warning>

## Steps

<Steps>
  <Step title="See what would break">
    ```bash
    beaver cloud impact srv_web02 --cloud paperclip-prod
    ```
    Shows what breaks if this node is lost. Read-only.
  </Step>
  <Step title="Stop sending it new work">
    ```bash
    beaver cloud machines cordon srv_web02 --cloud paperclip-prod
    ```
    The node takes nothing new. Its **existing containers keep running**. Cordoning the cloud's only host while work runs asks for `--yes`.
  </Step>
  <Step title="Move what runs there">
    Preview, then drain:
    ```bash
    beaver cloud machines drain srv_web02 --cloud paperclip-prod --plan
    beaver cloud machines drain srv_web02 --cloud paperclip-prod --yes
    ```
    The preview changes nothing and lists every **blocker**. Databases and anything with volumes are never moved automatically — they are reported and nothing moves. The machine stays
    cordoned afterwards, whatever the outcome.

    Prefer to review the plan step by step? `beaver cloud evacuate srv_web02 --cloud paperclip-prod` writes a **reviewable plan** and moves nothing; run it with
    `beaver cloud evacuate execute <plan-id>`, and undo it with `beaver cloud evacuate rollback`.
  </Step>
  <Step title="Do the maintenance">
    Reboot with `beaver machine reboot <machine>` — first check `beaver machine reboot-impact <machine>` to see what it would interrupt. Or retire it with
    `beaver cloud machines rm srv_web02` and `beaver machine remove <machine-id>`.
  </Step>
</Steps>

## Bring it back

`beaver cloud machines uncordon srv_web02 --cloud paperclip-prod` lets it take new work again — if its hosting setting is on. A machine that was turned to *member only* stays that way
until `beaver cloud machine policy srv_web02 --cloud paperclip-prod --host=on`. (`beaver cloud undrain` undoes the older leaving state.)

## What this does not protect

Read the evacuation plan carefully before you execute it, especially for anything that stores data, and have [backups](/data/backups-and-restore) in place first.

## If it fails

`impact` or `evacuate` need the cloud and machine names — list them with `beaver cloud list` and `beaver cloud machines <cloud>`. If the machine is already offline, see
[Machine shows offline](/operate/troubleshoot-machine-offline).
