## Managed, Stateful, Yours

A Beaver Service is a stateful dependency — a database, cache, or message broker — provisioned
onto your own connected infrastructure and operated as part of the platform. Attach one to
your application and it receives connection details as an environment variable; Beaver
handles day-to-day operation, backups, and version upgrades.

## The Same Workflow, Every Type

<Steps>
  <Step title="Provision it">
    ```bash
    beaver service create paperclip-db --type postgres
    ```
    Omit `--type` for an interactive picker, or `--version` to pin a specific version — see
    [`beaver service catalog`](/cli/service#catalog--provisioning) for what's available.
  </Step>
  <Step title="Attach it to your application">
    ```bash
    beaver service attach paperclip-db --container paperclip-web
    ```
    Your application receives a connection string as an environment variable. It can use it
    once the attachment takes effect — for most services, that's your next deployment.
  </Step>
  <Step title="Manage it">
    ```bash
    beaver service show paperclip-db
    beaver service backup paperclip-db
    beaver service resize paperclip-db --cpu 2 --memory 2048
    ```
    Resize resources, schedule backups, reveal credentials, or upgrade the version, all
    without re-provisioning from scratch.
  </Step>
</Steps>

<Warning>
  Deleting a service permanently removes its data. Detaching an application from a service
  does not delete the service or its data — delete the service separately if that's what you
  intend.
</Warning>

## Higher Availability

For types that support it, `beaver service cluster` provisions a multi-member cluster
instead of a single instance:

```bash
beaver service cluster create paperclip-queue --type kafka --replicas 3
```

See [Service clusters](/data/high-availability) for when this is worth the extra members.
