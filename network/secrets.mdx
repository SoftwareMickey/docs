You handle three kinds of secret with Beaver. For each: where it lives, what shows it, and what you must not do.

<Tabs>
  <Tab title="Dashboard">A deployment's **Environment** tab holds its variables.</Tab>
  <Tab title="CLI">`beaver environment vars` — shown in the table below.</Tab>
</Tabs>

| Secret | Lives | Revealed by | Don't |
| --- | --- | --- | --- |
| **Application variables** (API keys, URLs) | Per [environment](/deploy/environments), applied at deploy | Dashboard **Environment** tab; `beaver environment vars` (names only unless `--reveal`) | Commit them or `COPY` a `.env` file into the image |
| **Docker Hub login** | On your Builder machine (`docker login`) | `beaver docker --auth` shows its state, not the password | Use a personal account you cannot rotate for a shared Builder |
| **Repository access** | The Beaver GitHub App's grant on the repositories you chose | `beaver github` shows each connection's health | Grant more repositories than you need |

## Habits

- **Rotate** a database credential at the database, then update the variable and redeploy ([Connection strings and secrets](/data/connection-strings-and-secrets)); give each application its own login.
- **Never pass a secret on a command line** you keep in shell history; use `--env-file` (and keep that file out of git).
- In a team workspace, revealing secrets in a **protected environment** needs approval unless an Owner or Admin enabled `developer_secrets`
  ([Production approvals](/teams/production-approvals)); every reveal appears in the workspace [audit history](/teams/audit-history).
- A `BEAVER_TOKEN` used in CI is your **session token** — treat it as a secret ([Deploy from CI](/deploy/ci-cd)).
