This page is for the question a security review actually asks: **if Beaver's own database were
breached, what could the attacker read?** It describes the mechanism as shipped (crypto scheme
version 1), not the design intent — if the scheme ever changes, this page is updated to match,
or removed if it would otherwise go stale.

## The claim, in one sentence

An environment variable's **value** is encrypted on the device that creates it (your browser, or
the Beaver CLI/Agent) against the **specific machine** that will run it — Beaver's own servers
never hold a key that can open it, and never see the plaintext in the ordinary read/write/deploy
path.

## Who holds which half

Each machine you enroll (`beaver connect`) generates its own encryption keypair locally — an
X25519 keypair, separate from that machine's WireGuard key and its separate mTLS identity key, so
one compromised key never implicates the other two unrelated protocols.

| Half | Where it lives | Leaves the machine? |
| --- | --- | --- |
| **Private key** | `/etc/beaver/secrets/identity.key` on that one machine, root-owned, mode `0600` | Never — not transmitted, not logged, not backed up by Beaver |
| **Public key** | Beaver's database (`EnrolledServer.SecretsPublicKey`) | Yes — by design, anyone authorized to set a secret for that machine fetches it to encrypt against |

A public key being public is not a weakness here: **anonymous sealing** (the construction below)
means holding the public key lets you *encrypt* for that machine, never *decrypt* anything sealed
under it.

## The construction: a sealed box

Every sealed value is a [sealed box](https://doc.libsodium.org/public-key_cryptography/sealed_boxes)
— `crypto_box_seal`, the same construction libsodium and NaCl use, implemented independently in
Go (the CLI and Beaver's own servers) and TypeScript (the desktop app's shared
`@beaver/env-crypto` package) against the same envelope format, with a cross-language test that
fails the build if the two implementations ever disagree on a single byte.

Sealing a value for a machine:

1. The sender (your browser, the CLI) generates a one-time, throwaway keypair — used once, then
   discarded. It never has any relationship to your own identity.
2. It combines that throwaway private key with the **destination machine's public key** to derive
   a shared secret, and encrypts the value with it (XSalsa20-Poly1305).
3. The envelope stored in Beaver's database is: the throwaway *public* key, plus the ciphertext.
   The throwaway private key is gone the moment step 2 finishes — nothing retains it, anywhere.

Opening it requires the **destination machine's private key** — the one thing that never left
that machine's disk. Nothing else can derive the same shared secret, including Beaver's own
servers, which only ever handle the envelope as opaque bytes.

## What a database breach would expose

| Attacker has | Can read |
| --- | --- |
| A full copy of Beaver's database (every table, every row) | Every machine's **public** key, every sealed **ciphertext** — and nothing decryptable from either, without also having the specific machine's private key |
| One machine's `/etc/beaver/secrets/identity.key` | Only the sealed values currently assigned to **that machine** — not other machines', and not anything already migrated off it |
| Both of the above together | Only what the stolen private key(s) can open — the breach's blast radius is the machines whose keys were taken, never "every secret in the workspace" |

What this does **not** protect against: a machine that is itself compromised while running (the
plaintext exists briefly in that machine's own process memory the moment it unseals a value to
actually use it — this is true of any encryption-at-rest scheme and isn't specific to Beaver), or
a value you paste somewhere else after reading it.

## The trade-off: write-only, on purpose

Because Beaver's servers hold no key that can open a sealed value, **nothing — not the dashboard,
not the CLI, not Beaver's own support team — can show you a sealed value's current content after
you've set it.** The dashboard and `beaver environment vars diff --reveal` show a sealed row as
present but never its contents; a row stays legacy (server-decryptable, the older model) until
the project actually migrates to sealed storage.

This is deliberate, not a missing feature: the moment "show me the value" becomes possible again
anywhere on the server side, the breach blast radius above goes back to "everything." If you need
to confirm what you set, keep your own record of it (a password manager, your CI secret store) the
same way you would for any write-only credential.

## If you lose the machine

Only that one machine's private key can open values sealed for it. If the machine is lost or
destroyed with no backup of that key, those specific values are **permanently unrecoverable** —
there is no server-side escape hatch, by design (see the breach table above: a server-side way to
recover them would also be a server-side way to read them). The one deliberate exception is a
passphrase-protected recovery kit you export yourself, ahead of time, that only you can later
restore — see [Backups and restore](/data/backups-and-restore) and `beaver machine
export-recovery-kit --help`.
