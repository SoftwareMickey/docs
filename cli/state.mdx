## Purpose

`beaver state` shows three views of your project side by side, and gives you commands to
bring them back in sync when they disagree:

| View | What it is |
| --- | --- |
| **Local** | `.beaver/config.yml` in your working directory right now. |
| **Saved** | The configuration Beaver currently has on record for this project. |
| **Live** | What's actually running. |

Run `beaver state` bare for the default view (the same as `state status`).

## Syntax

```bash
beaver state <subcommand> [flags]
```

| Subcommand | Purpose |
| --- | --- |
| `status` | Compare all three views at once. |
| `drift` | Show the timeline of differences between the saved configuration and what's running. |
| `history` | Show the saved-configuration revision history. |
| `diff` | Show what changed between two versions of the configuration. |
| `pull` | Write the saved configuration into your local file. |
| `apply` | Save your local file as the new saved configuration and update the running deployment to match. |
| `rollback` | Restore an earlier saved revision. |

## Flags

<ParamField query="--env" type="string" default="">
  On `status`: compare against a named environment's override.
</ParamField>
<ParamField query="--watch" type="boolean" default="false">
  On `status`: re-check on an interval until interrupted.
</ParamField>
<ParamField query="--force" type="boolean" default="false">
  On `pull`: overwrite local edits even if they haven't been saved yet.
</ParamField>
<ParamField query="--dest" type="string" default="">
  On `pull`: write to this directory instead of your working tree, without touching it.
</ParamField>
<ParamField query="--no-reconcile" type="boolean" default="false">
  On `apply`/`rollback`: record the configuration change, but don't also update what's
  currently running.
</ParamField>
<ParamField query="--to" type="string" default="">
  On `rollback`: the revision to restore — its full ID, or the first characters shown by
  `beaver state history` (at least 6). Defaults to the revision immediately before the
  current one.
</ParamField>
<ParamField query="--limit" type="integer" default="50">
  On `history`: how many revisions to show per page (at most 200).
</ParamField>
<ParamField query="--before" type="string" default="">
  On `history`: show revisions older than this one (its ID or the first characters shown in
  the table). The footer prints the exact command for the next page.
</ParamField>
<ParamField query="--local" type="boolean" default="false">
  On `diff`: compare the given revision against your local file instead of the saved
  configuration.
</ParamField>
<ParamField query="--plan" type="boolean" default="false">
  On `rollback`: show the target revision and what would change, without applying it.
</ParamField>

## What each command shows

`status` runs two comparisons in one place: whether your local file has changes not yet
saved (or the saved configuration changed elsewhere — a dashboard edit, a teammate's push),
and whether the running deployment actually matches what's saved. It's read-only and exits
non-zero if anything is out of sync — useful as a CI gate.

`drift` shows **what has changed** between the saved configuration and what's running: one
row per field that drifted, when it was first detected, and when (if ever) it cleared. It
doesn't change anything itself.

`history` lists past saved-configuration revisions, newest first, each with a short ID you can
paste into `rollback --to` or `diff`. The one that matches what's saved right now is marked
`current`, and a revision created by a rollback says which one it restored. Older revisions
are kept for a limited time (see [Versions and fingerprints](/operate/state-and-drift#versions-and-fingerprints)).

`diff` compares two versions by **what they mean**: comments, spacing, quoting and key order
are ignored, and values under keys that look like secrets are never printed. With no
arguments it compares your local file with what's saved; with one revision it compares that
revision with what's saved (or with your local file, using `--local`); with two it compares
them with each other. It exits `1` when they differ and `0` when they don't, like
`git diff --exit-code`.

When Beaver knows which saved revision is deployed, `status` also shows it:

```text
  recorded revision  3f2a91c0
  deployed revision  9b01d4e7
```

If a newer revision is saved than the one that's deployed, or the last deploy failed, `status`
says so and exits non-zero.

## Consequences

`apply` makes your currently checked-out `.beaver/config.yml` the new saved configuration and
updates the running deployment to match it. It's built for CI — run it on a push to your main
branch so a merged config change takes effect automatically. It's idempotent (safe to run on
every push) and tags the resulting revision with the current git commit.

`pull` refuses to overwrite local edits that haven't been saved yet, unless `--force`; it
writes a `.beaver/config.yml.bak` backup first.

`status` and `apply` judge your file by what it **means**, not how it's typed. Adding a
comment, reordering keys or changing indentation doesn't make your file "ahead" of what's
saved, and `apply` of a formatting-only change records nothing new ("already matches").

<Warning>
  Rolling back restores your **saved configuration only**. Data, volumes and databases are not
  changed — if the newer revision added a database and your app wrote to it, going back doesn't
  un-write that data.
</Warning>

<Warning>
  `rollback` never rewrites history — restoring an earlier revision creates a **new** current
  revision copied from it. By default it also updates the running deployment to match; pass
  `--no-reconcile` to only record the change without touching what's running, or `--plan`
  first to preview exactly what would change.
</Warning>

## Examples

<Info>
  **Reviewed against source**: examples on this page were checked against `beaver-cli` source and its own `--help` output, not executed end-to-end against a live workspace.
</Info>

<CodeGroup>

```bash Check everything's in sync
beaver state status
```

```bash See what's drifted and when
beaver state drift
```

```bash Bring local in line with what's saved
beaver state pull
```

```bash Save local as new, and update the running deployment (CI)
beaver state apply
```

```bash Roll back, previewing first
beaver state history
beaver state rollback --plan
beaver state rollback --to 3f2a91c0
```

```bash See what a revision changed
beaver state diff 3f2a91c0
beaver state diff 3f2a91c0 9b01d4e7
```

</CodeGroup>

**Expected output** (`status`, reviewed against source):

```text
local vs recorded    up to date
recorded vs live     drifted — replicas: recorded 3, live 2
```

## Results & failures

| Situation | What you'll see | What to do |
| --- | --- | --- |
| `status` — everything in sync | Exit code 0, "up to date" for both comparisons | Nothing to do. |
| `status` — out of sync | The specific mismatch, non-zero exit | `pull` (adopt saved) or `apply`/push local changes, depending on which side should win. |
| `pull` with unsaved local edits | Refusal, unless `--force` | Save your edits (`beaver config push`) first, or `--force` to discard them. |
| `status` — only comments or formatting differ | "same content as the recorded state — only formatting or comments differ", exit code 0 | Nothing to do. |
| `status` — saved but not deployed | "a newer revision is saved than the one that is deployed", non-zero exit | `beaver deploy` to roll it out. |
| `status` — last deploy failed | The failed revision and the one still running, non-zero exit | Fix the cause and deploy again; the earlier revision keeps running meanwhile. |
| `rollback` success | "restored the saved config from revision … — recorded as revision …", plus a note that data was not changed | Verify with `state status`. |
| A revision ID matches more than one revision | The candidates, listed | Type a few more characters. |
| A revision ID matches nothing | "no revision matches …" | `beaver state history` lists them. |
