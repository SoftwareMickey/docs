## Purpose

A **Beaver Cloud** is a named pool of your own enrolled machines (see
[Infrastructure setup](/infrastructure/providers) for connecting individual machines). Once
machines are enrolled, `beaver cloud` is what you use to group them, give them a shared
private network, set capacity reservations, and decide how applications spread across the
pool — `beaver deploy --cloud <name>` then targets the pool instead of one machine.

## Lifecycle

| Subcommand | Purpose |
| --- | --- |
| `list` | List every cloud in your workspace. |
| `create <name>` | Create a cloud from a set of machines. |
| `status [cloud]` | Health, what needs attention, machines, capacity, network, and recent events. |
| `inspect [cloud]` | Every machine with its IDs, hostname, address, and capacity (`machines --wide`). |
| `rename <cloud> <new-name>` | Rename a cloud. |
| `rm [cloud]` | Delete a cloud (must have no machines). |
| `events [cloud]` | Event history: membership, network, capacity, placement, recovery. |

<ParamField query="--machines" type="string" default="">
  On `create`: comma-separated machine names or IDs to add.
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  On `rm`: skip the confirmation prompt. See [shared flags](/cli/shared-flags#yes).
</ParamField>
<ParamField query="--limit" type="integer" default="30">
  On `events`: maximum events to show. On `placements`: how many recent decisions to show
  (default `10`, `0` for all).
</ParamField>
<ParamField query="--wide" type="boolean" default="false">
  On `status`, `machines`, `capacity`, `network`, `gateway` and `workspace ls`: also show machine
  IDs and hostnames. Tables otherwise name machines only.
</ParamField>
<ParamField query="--category" type="string" default="">
  On `events`: filter by category — `membership`, `network`, `capacity`, `placement`, or
  `recovery`.
</ParamField>

`status` and `inspect`'s network reachability is a **separate, observable axis** from the
cloud's own `status` field — a cloud can be up while one node's network connectivity is
degraded, or vice versa. Check both when diagnosing an issue rather than assuming they always
move together.

### Reading the output

Every read command lays its report out the same way:

```text
MICKEY_NET · Capacity
● Healthy · 2 of 2 machines ready

ATTENTION                       (only when something needs you)
  ✗ hosting-01 is offline. Its 4 cores and 7.6 GB are not available for new workloads.
    → beaver machine overview hosting-01

AVAILABLE FOR NEW WORKLOADS     (the direct answer)
MACHINES                        (the detail behind it)
NEXT                            (useful follow-up commands)

Updated 12:19 PM · 873ms
```

- **Machines are named, not numbered.** A machine shows as its name, else its hostname, else its
  full machine ID. Wherever a command takes a `<machine>` (or `--machine`, `--node`, `--pin`),
  you can give the name, the hostname, the machine ID, or a unique start of the ID.
- **Machine states** are the same words everywhere: `Ready`, `Draining`, `Joining`,
  `Awaiting approval`, `Offline`, `No hardware facts`, `Not schedulable`, `Failed to join`.
- **The first line under the title is the verdict.** It never reads `Healthy` while the
  ATTENTION block lists a problem — it says `Needs attention` instead.
- Tables fit the terminal: on a narrow one the least important columns give way first, and a
  table that still cannot fit becomes one short card per row. Piped output is plain text at 100
  columns (or `$COLUMNS`); `NO_COLOR` turns colour off and every status keeps its word and marker.
- `--json` / `--output yaml` print the server's document unchanged; `--quiet` drops the footer.

## Machines & membership

| Subcommand | Purpose |
| --- | --- |
| `machines [cloud]` | A cloud's machines: state, role, private address, and free capacity. |
| `machines add [machine...]` | Add machines to a cloud. |
| `machines rm [machine]` | Remove a machine from a cloud. |
| `machines pending [cloud]` | List machines awaiting operator approval to join a cloud. |
| `machines approve <machine>` | Approve a pending machine. |
| `machines reject <machine>` | Reject a pending machine. |
| `preflight <machine>...` | Check machines for cloud-membership readiness before adding them. |

<ParamField query="--cloud" type="string" default="">
  Cloud slug or name for `machines` subcommands. Interactive picker if omitted.
</ParamField>
<ParamField query="--override" type="string" default="">
  On `machines add`: preflight finding IDs to admit past, for findings you've reviewed and
  intentionally want to proceed despite.
</ParamField>
<ParamField query="--from-workspace" type="string" default="">
  On `machines add`: contribute a machine belonging to a different workspace you're also a
  member of, without switching your session's active workspace first. See [Sharing with
  another workspace](#sharing-with-another-workspace).
</ParamField>
<ParamField query="--check" type="boolean" default="false">
  On `machines add`: evaluate every requirement for joining and report which are met and which
  are not, without adding the machine. Exits `1` when the machine cannot join. Cannot be combined
  with `--fix`.
</ParamField>
<ParamField query="--fix" type="boolean" default="false">
  On `machines add`: repair what Beaver can repair safely on the machine (missing WireGuard
  tooling, IP forwarding, time sync), then add it. Asks first; only repairs the server marks
  automatic and safe are run, and only on the machine being added. Anything else is printed as an
  instruction, never run.

  If the machine's agent can't run system tasks unattended (its `sudo` asks for a password) and
  you're on that machine, `--fix` explains the change, asks, lets `sudo` ask for your password
  once, then retries the join. This is the same step as
  [`beaver agent privileges grant`](/cli/agent#unattended-privileges). From another machine it
  prints the command to run on the target instead, because only someone on that machine can type
  its password.
</ParamField>
<ParamField query="--explain" type="boolean" default="false">
  On `machines add`: list every requirement that was evaluated, including the ones that were met.
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  On `machines add --fix`, `machines rm` and `machines reject`: accept the described change
  without the confirmation prompt. Without a terminal, these commands fail and tell you to pass
  `--yes` — they never wait for input or quietly do nothing. `--yes` never bypasses a requirement
  that is not met.
</ParamField>
<ParamField query="--force" type="boolean" default="false">
  On `machines rm`: accept the one impact the refusal listed — taking running workloads down
  (every replica of an app, a stateful workload's data node, or the cloud's last gateway). It is
  not a general override.
</ParamField>
<ParamField query="--json / --output / --quiet" type="flags" default="">
  On `machines add`: `--json` (or `--output json|yaml`) prints structured output, including
  failures; `--quiet` hides routine status lines but never an error.
</ParamField>
<ParamField query="--cloud" type="string" default="">
  On `preflight`: re-check the members of this existing cloud instead of a fresh set.
</ParamField>
<ParamField query="--cidr" type="string" default="">
  On `preflight`: check a specific overlay network address range for collisions instead of
  letting Beaver propose one.
</ParamField>
<ParamField query="--fix" type="boolean" default="false">
  On `preflight`: install missing prerequisites on the machines, then re-check.
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  On `preflight`: skip the `--fix` confirmation prompt.
</ParamField>

Once a cloud's join policy is `approval_required` (this happens automatically once a second
workspace holds a grant on it, or its private network is active — see [Sharing with another
workspace](#sharing-with-another-workspace)), a contributed machine sits in `machines pending`
until an operator approves or rejects it, instead of joining immediately.

## Sharing with another workspace

<Info>
  [Sharing a Beaver Cloud across workspaces](/teams/cloud-sharing) explains grants, roles
  and quotas before diving into syntax.
</Info>

| Subcommand | Purpose |
| --- | --- |
| `workspace ls` | List every workspace holding a grant on a cloud, with role, status and quota. |
| `workspace invite <workspace-id>` | Invite a workspace onto this cloud. |
| `workspace remove <workspace-id>` | Revoke a workspace's grant (staged, then confirmed). |

<ParamField query="--cloud" type="string" default="">
  Cloud slug or name for `workspace` subcommands. Interactive picker if omitted.
</ParamField>
<ParamField query="--role" type="string" default="consumer">
  On `workspace invite`: `consumer`, `contributor`, `operator` or `admin`.
</ParamField>
<ParamField query="--max-cpu" type="integer" default="0">
  On `workspace invite`: a quota ceiling in CPU cores (0 = unlimited).
</ParamField>
<ParamField query="--max-memory" type="integer" default="0">
  On `workspace invite`: a quota ceiling in MB (0 = unlimited).
</ParamField>
<ParamField query="--confirm" type="boolean" default="false">
  On `workspace remove`: finish a staged revoke. Without it, the first call only reports the
  impact and stages the grant to `termination_pending` — existing workloads keep running,
  only new deploys from that workspace are blocked.
</ParamField>

There is no directory to search — an invited workspace's ID is shared with you directly by
whoever administers it. `workspace invite` prints a one-time token; the invited workspace's
admin accepts it with `beaver workspace cloud accept <token>` (see [`beaver
workspace`](/cli/workspace#cloud)), the counterpart command from the invited side. The same
page also covers requesting access to a cloud you don't hold a grant on yet
(`beaver workspace cloud request`), and approving or denying those requests
(`beaver workspace cloud approve`/`deny`).

`machines add --from-workspace <workspace>` contributes a machine belonging to a workspace
you're also a member of, without switching your whole session's active workspace — the
backend still checks you're actually a member of that workspace, so this never lets you
impersonate a workspace you don't belong to.

## Network

| Subcommand | Purpose |
| --- | --- |
| `network [cloud]` | The private network: whether every machine is connected, latency, and container subnets. |
| `network enable <cloud>` | Turn on the private network for a cloud. |
| `network allows [cloud]` | List cross-project network allow rules. |
| `network allows add [cloud]` | Allow two projects to reach each other over the private network. |

| `gateway [cloud]` | Which machines take public traffic, and whether each is serving. |

## Public ingress

A cloud's stable public IP and hostname; see [Public IP and private name of a cloud](/network/cloud-ingress).

| Subcommand | Purpose |
| --- | --- |
| `ingress [cloud]` | The public IP, hostname, mode, private name, gateways serving, and the domains using the address. Same as `ingress show`. |
| `ingress status [cloud]` | One line; exits non-zero unless the ingress is active, so scripts can gate on it. |
| `ingress enable [cloud]` | Give the cloud a public address. Running it again changes nothing. |
| `ingress disable [cloud]` | Release the address. Refused while domains are attached, and the refusal names them. |
| `ingress probe [cloud]` | Re-check the ingress now instead of waiting for the next automatic check. |
| `ingress guard <mode> [cloud]` | `off`, `observe` or `enforce`: restrict gateways to accept public traffic only through the cloud's address. |

<ParamField query="--dedicated" type="boolean" default="false">
  On `ingress enable`: ask for an address that belongs to this cloud alone (may be billed separately).
</ParamField>
<ParamField query="--explain" type="boolean" default="false">
  On `ingress`, `ingress show` and `ingress probe`: also explain how the address and status work.
</ParamField>
<ParamField query="--force" type="boolean" default="false">
  On `ingress guard`: allow `enforce` without a prior observe period. It never skips the check that the cloud's address currently reaches every gateway.
</ParamField>

Adding or removing a gateway needs no DNS change when a cloud has public ingress, and `gateway add` says so.

<ParamField query="--matrix" type="boolean" default="false">
  On `network`: include the full node-to-node connectivity matrix.
</ParamField>
<ParamField query="--debug" type="boolean" default="false">
  On `network`: add each machine's tunnel endpoint and the MTU detail of the container
  network. Advanced/troubleshooting use — not needed for routine checks.
</ParamField>
<ParamField query="--cidr" type="string" default="">
  On `network enable`: overlay address range to use. Proposed automatically if omitted.
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  On `network enable`/`network allows add`/`gateway add`: skip the confirmation prompt.
</ParamField>
<ParamField query="--project-a" type="string" default="" required>
  On `network allows add`: first project ID. Required.
</ParamField>
<ParamField query="--project-b" type="string" default="" required>
  On `network allows add`: second project ID. Required.
</ParamField>
<ParamField query="--cloud" type="string" default="">
  On `gateway add`: cloud slug or name. Interactive if omitted.
</ParamField>

A cloud's private network lets its member machines reach each other directly; `network
allows` controls which **projects** (not just machines) may cross that network to reach each
other. A **gateway** is a member machine that also accepts public inbound traffic on behalf
of the cloud — `gateway`/`gateway add`/`gateway rm` manage which machines have that role.

## Capacity & reservations

| Subcommand | Purpose |
| --- | --- |
| `capacity [cloud]` | How much CPU and memory is available for new workloads, the largest workload that fits, and each machine's share. |
| `capacity node [cloud]` | One machine's capacity, line by line. |
| `capacity trend [cloud]` | Available capacity over the last 30 days, and when it would run out. |
| `reserve [cloud]` | The system reserve each machine keeps. |
| `reserve set [cloud]` | Change the system reserve (cloud-wide, or `--node` for one machine). |
| `reserve clear [cloud]` | Go back to the default reserve. |

<ParamField query="--explain" type="boolean" default="false">
  On `capacity`: show how hardware becomes available capacity, line by line, for CPU, memory
  and disk.
</ParamField>
<ParamField query="--machine" type="string" default="">
  On `capacity node`: the machine to show (name, hostname or ID). A picker opens if omitted and
  the cloud has more than one machine; without a terminal, `--machine` is required.
</ParamField>
<ParamField query="--node" type="string" default="">
  On `reserve set`/`reserve clear`: apply to (or clear) one machine's reserve — by name,
  hostname or ID — instead of the cloud-wide one.
</ParamField>
<ParamField query="--cpu" type="number" default="0">
  On `reserve set`: CPU cores to reserve.
</ParamField>
<ParamField query="--memory" type="integer" default="0">
  On `reserve set`: memory in MB to reserve.
</ParamField>
<ParamField query="--disk" type="number" default="0">
  On `reserve set`: disk in GB to reserve.
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  On `reserve set`/`reserve clear`: skip the confirmation prompt.
</ParamField>

**What the capacity numbers mean.** `--explain` prints exactly this, per resource:

| Line | Meaning |
| --- | --- |
| Hardware | Every machine's CPU, memory and disk. |
| − System overhead | The system reserve: what each machine keeps for the OS, the Beaver agent, the proxy and exporters. |
| − Workload reservations | What workloads already placed on the cloud asked for. |
| − Placements in progress | Held for replicas being placed right now. |
| − Unavailable machines | The whole hardware of machines that cannot take work: offline, draining, joining, awaiting approval, or not yet reporting their hardware. |
| = Available | What a new workload can use. |
| Live usage | Measured usage. It is shown for context and never subtracted — a quiet workload still holds its reservation. |

The bar beside each headline number is filled for what is in use (reserved or unavailable)
and empty for what is free. The system reserve lowers what's available for new deployments
without affecting what's already running.

## Workload placement

| Subcommand | Purpose |
| --- | --- |
| `workload [cloud]` | Where each application runs: spread, packed, or pinned, and where its data lives. |
| `workload set [cloud] <container>` | Set an application's placement policy. |
| `placements [cloud]` | Why each replica landed where it did: every machine considered, the one chosen, and why others were left out. |

<ParamField query="--policy" type="string" default="">
  On `workload set`: placement policy — `spread` (default: one replica per node where
  possible), `pack` (consolidate onto the fewest nodes), or `pinned` (every replica on one
  named node).
</ParamField>
<ParamField query="--pin" type="string" default="">
  On `workload set`: the machine to pin to (name, hostname or ID). With `--policy pinned` and no
  `--pin`, a picker opens.
</ParamField>
<ParamField query="--lb" type="string" default="">
  On `workload set`: internal load balancing mode — `dns` (multi-record round-robin) or
  `proxy` (through the node's local proxy).
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  On `workload set`: skip the confirmation prompt.
</ParamField>

`workload` describes **intent** — what the cloud is asked to do — distinct from `placements`,
which is the **history** of what actually happened (deploy-host picks and scaling decisions
already made). Replica *count* is governed by [`beaver scaling`](/cli/scaling); `workload set`
only decides where those replicas land, not how many there are.

## Recovery

| Subcommand | Purpose |
| --- | --- |
| `impact <machine>` | What breaks if this machine is lost — a verdict (`Safe to lose`, `Risky to lose`, `Losing it causes an outage`), then each workload's outcome. |
| `drain <machine>` | Stop placing **new** work on a machine; what runs there keeps running. |
| `undrain <machine>` | Let a drained machine take new work again. |
| `evacuate <machine>` | Compute a **reviewable plan** to move every workload off a machine. Moves nothing by itself. |
| `evacuate execute <plan-id>` | Run a previously generated evacuation plan. |
| `evacuate rollback` | Undo an executed evacuation plan, moving containers back. |

<ParamField query="--cloud" type="string" default="">
  On every recovery subcommand: cloud slug or name. Interactive picker if omitted.
</ParamField>
<ParamField query="--yes" type="boolean" default="false">
  Skip the confirmation prompt. See [shared flags](/cli/shared-flags#yes).
</ParamField>

`drain` marks a node as draining — it is excluded from new placement decisions, but its existing containers keep running. `evacuate` is the separate step that actually moves
them: it generates a plan without moving anything, you review it, then `evacuate execute <plan-id>` runs it. A cloud does **not** reschedule work on its own when a machine goes
offline (there is no automatic failover), so these are the explicit recovery actions. See [Drain and evacuate a machine](/infrastructure/drain-and-evacuate).

## Services & containers

| Subcommand | Purpose |
| --- | --- |
| `services [cloud]` | Service discovery: every app in the cloud, how many replicas are healthy, and the addresses its name resolves to. |
| `containers [cloud]` | Every container deployed to the cloud, and the machine, address and subnet each replica runs in. |

Service discovery is a property of the cloud, not of any one host: each app resolves
cloud-wide by its short name (`api`) and by a full name (`api.<slug>.beaver.internal`) to
every healthy replica's address on the cloud's private network — this is what your other
services should use to reach it, rather than a specific machine's address. `containers`
gives you the reverse view: where each replica actually landed.

Distinct from [`beaver service`](/cli/service) (provisioning and operating managed stateful
dependencies like databases) and [`beaver containers`](/cli/containers) (every deployed
container across your whole workspace, not scoped to one cloud).

## Consequences

<Warning>
  `rm` only succeeds on an empty cloud (no member machines) — remove machines with `machines
  rm` first if you need to delete a cloud that still has members.
</Warning>

Adding or removing a machine (`machines add`/`machines rm`) changes what's schedulable across
the cloud going forward; it does not itself move or restart anything already running on
another member. `network enable` and gateway changes can briefly interrupt cross-node
connectivity while they take effect.

## Examples

<Info>
  **Reviewed against source**: examples on this page were checked against `beaver-cli` source and its own `--help` output, not executed end-to-end against a live workspace.
</Info>

<CodeGroup>

```bash Create a cloud
beaver cloud create paperclip-prod --machines web01,web02,db01
```

```bash Check capacity before deploying
beaver cloud capacity paperclip-prod
```

```bash Deploy into the cloud
beaver deploy --cloud paperclip-prod
```

```bash Spread an app, then pin the database
beaver cloud workload set paperclip-prod paperclip-web --policy spread
beaver cloud workload set paperclip-prod paperclip-db --policy pinned --pin db01
```

```bash See how capacity adds up
beaver cloud capacity paperclip-prod --explain
beaver cloud capacity node paperclip-prod --machine web01
```

```bash Before taking a machine down
beaver cloud impact web02 --cloud paperclip-prod
beaver cloud drain web02 --cloud paperclip-prod
```

</CodeGroup>

## Results & failures

| Situation | What you'll see | What to do |
| --- | --- | --- |
| `create` success | The new cloud with its member machines | Deploy with `--cloud <name>`. |
| `rm` on a non-empty cloud | An error requiring an empty cloud first | Remove all members with `machines rm`, then retry. |
| `machines add` cannot join | Every requirement with ✓/✕/!, what is wrong, the repair for each, the command to retry, and "No changes were made." | Run the repair shown (`--fix` does the automatic ones), or pass `--override` with reviewed finding IDs. |
| `machines add --check` | The same requirements, nothing changed. Exit `0` if it can join, `1` if not | Fix what is listed, then add the machine. |
| `machines add --fix` with no terminal and no `--yes` | A failure saying it needs confirmation | Re-run with `--fix --yes`. |
| `machines add` — "Agent cannot run system tasks unattended" | The failed requirement, naming the machine and `beaver agent privileges grant` | On that machine run `beaver agent privileges grant`, or `machines add --fix` there; then retry. |
| `machines rm` would take workloads down | The workloads and gateways affected, a safe alternative, and the `--force` command | Scale the app out first, or accept the impact with `--force`. |
| `machines rm` with no terminal and no `--yes` | A failure saying it needs confirmation (exit `1`) | Re-run with `--yes`. |
| `workload set --policy pinned` with no `--pin` | A machine picker (no terminal: an error) | Pass `--pin <machine>`. |
| A `<machine>` that matches nothing | `no machine named "x" in <cloud>`, listing the cloud's machines | Use one of the listed names. |
| A `<machine>` that matches several | The matching machine IDs | Pass the full machine ID. |
| `capacity node` with no terminal and no `--machine` | An error asking for `--machine` | Pass `--machine <machine>`. |
