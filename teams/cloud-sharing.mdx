## Cloud, workspace, and machine — three different questions

These three concepts get confused because sharing makes all three visible on the same
screen at once, but each still answers a different question, and none of them contains the
others:

| | Answers |
| --- | --- |
| **Workspace** | Who owns this application, and who pays for what it uses? |
| **Cloud** | Where can this application run? |
| **Machine** | What contributes the capacity a cloud is built from? |

Before sharing, one workspace usually answered all three questions for its own clouds — it
owned the cloud, ran the applications, and enrolled the machines. Sharing separates them: a
cloud can be **administered** by one workspace, **deployed into** by several, and **built
from machines contributed by** more than one of them, all at once.

## The model in one picture

A workspace holding a **grant** on a cloud is what "sharing" actually means — there is no
separate membership list, no organization entity, and no cross-customer marketplace. A grant
is a row that says: this workspace, this cloud, this role, these quota limits, this status.

```
Cloud "company-production"
├── Grant: Platform workspace   → role: admin      (the owner — always exists)
├── Grant: Payments workspace   → role: consumer    (deploys, doesn't administer)
└── Grant: Billing workspace    → role: contributor (adds a machine, deploys)
```

Every cloud has always had exactly one implicit grant — its owner's. Sharing doesn't change
that; it adds the ability for a second, third, or further grant to exist on the same cloud.
**A cloud with only its owner's grant behaves exactly as it always has** — this is true by
construction, not by convention: the single-grant case is the same code path a cloud without
sharing takes.

## Roles, in order of capability

| Role | Deploy | Add machines | Operate machines (drain/evacuate) | Manage the cloud (invite/revoke grants) |
| --- | --- | --- | --- | --- |
| **Consumer** | ✓ | | | |
| **Contributor** | ✓ | ✓ | | |
| **Operator** | ✓ | ✓ | ✓ | |
| **Admin** | ✓ | ✓ | ✓ | ✓ |

A workspace's role is set when its grant is created (by invite or by an approved request) and
can be changed by re-issuing the grant. The cloud's owner workspace always holds an `admin`
grant — that grant is marked `is_default` and can't be revoked, mirroring the fact that
someone has to remain accountable for the cloud existing at all.

## Getting a grant: invite or request

There is no directory of clouds or workspaces to browse. Two workspaces sharing a cloud have
always known about each other some other way first — the same account, the same company, a
direct conversation — and that's deliberate: this is **same-account sharing**, not a
cross-customer cloud marketplace.

**Invite** — the cloud's admin starts it:

```bash
beaver cloud workspace invite <workspace-id> --cloud production --role consumer --max-cpu 8
```

This prints a one-time token. The invited workspace's admin accepts it:

```bash
beaver workspace cloud accept <token>
```

**Request** — the workspace wanting access starts it instead, when it already knows the
cloud's ID:

```bash
beaver workspace cloud request <cloud-id> --role consumer --max-cpu 8
```

The cloud's admin then approves or denies it, optionally on different terms than asked for:

```bash
beaver workspace cloud approve <request-id> --max-cpu 4
```

Both paths end at the same place: a `WorkspaceGrant` row, active, with a role and quota. See
the [`beaver cloud`](/cli/cloud#sharing-with-another-workspace) and
[`beaver workspace`](/cli/workspace#cloud) command references for every flag.

## Quotas: two different ceilings

A grant carries two numbers that are easy to conflate:

- **Max CPU / Max memory** — the ceiling on what that workspace may *deploy* onto this cloud.
  Exceeding it refuses the deployment with a quota-specific `409`, distinct from the cloud
  simply being out of room.
- **Reserved CPU / Reserved memory** — a floor: capacity set aside for that workspace even
  when other workspaces are consuming heavily, so a noisy neighbor on the same cloud can't
  starve a workspace of the capacity its grant promised it.

Both are optional. A grant with neither set has no ceiling and no floor beyond the cloud's
own total capacity.

## Contributed machines

Adding a machine to a shared cloud works the same `beaver cloud machines add` you already
know, with one addition: **who contributed it is remembered**, separately from who
administers the cloud.

```bash
beaver cloud machines add prod-node-04 --cloud production --from-workspace billing-team
```

Once a cloud has more than one grant (or its private network is on), adding a machine stops
being unrestricted — new machines land in an approval queue instead of joining immediately:

```bash
beaver cloud machines pending --cloud production
beaver cloud machines approve <machine-id> --cloud production
```

A contributed machine's own workspace can withdraw it later (refused while it's still running
workloads, unless an operator forces it); nobody else can remove it without operator
authority. In every product surface, a machine contributed by a workspace other than the
active one shows a **"contributed by `<workspace>`"** badge — you're never looking at a
machine and assuming it's yours when it isn't.

## Network isolation

Two workspaces sharing a cloud do **not** default to being able to reach each other's
containers. Each workspace's containers sit in their own segment of the cloud's private
network, with default-deny between workspaces — the same posture the cloud already has
against the outside world, just applied one level deeper. If two workspaces' applications
genuinely need to talk to each other (a shared cache, an internal API), that's an explicit,
mutual-consent allow-list — both workspaces have to agree, not just one.

## What each workspace can see

Logs, metrics, events, and exec access stay scoped to your own workspace's containers, even
on a cloud you don't administer. What you *do* see, regardless of role, is the cloud's own
health — machine counts, capacity, network status — because that's infrastructure state, not
application data. An operator-safe dashboard exists specifically so someone troubleshooting
the cloud can see enough to help without being handed another workspace's secrets or logs.

## Billing: consumption vs. contribution

Every workload is billed to the workspace that deployed it, not to the cloud's owner — a
consumer workspace deploying onto shared production capacity pays for its own consumption,
exactly as if it had its own cloud. The cloud's owner separately sees a cloud-level cost
line for anything above and beyond what individual workspaces are billed for.

Contributing a machine is **never monetized** — a workspace that adds hardware to a shared
cloud doesn't get billed less, and doesn't bill others, for the capacity it contributed. This
is deliberate: mixing "what you used" and "what you gave" into one number would make neither
trustworthy. `beaver cloud status` and the cloud settings page both show the two
side by side, never combined into a single figure.

## Recovery survives a workspace boundary

If a machine fails, a workload recovers onto any eligible machine in the cloud — regardless
of which workspace contributed the machine it lands on. The impact report names both
workspaces involved (whose workload moved, whose machine it moved onto) so attribution stays
correct even when recovery crosses a workspace boundary. Evacuating a contributed machine on
purpose (not a failure — an intentional drain) requires either operator authority or the
contributing workspace's own consent; nobody else can decide to empty out a machine that
isn't theirs.

## Existing clouds need no action

**This is the central promise of sharing: it's additive, never a migration.** A cloud with a
single workspace's grant — which is every cloud that existed before sharing, and every new
cloud until you explicitly invite or approve a second grant — behaves byte-for-byte
identically to how it always has. Nothing here is reachable until you deliberately invite a
second workspace or approve a request; there is no opt-in step required to keep behaving
exactly as before.
