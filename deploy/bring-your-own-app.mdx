**Beaver deploys React applications.** Vite and Create React App are both React as far as Beaver is concerned; so is a React app you wired up yourself.

Within that, Beaver is incurious about your app. You bring the Dockerfile and Beaver builds it exactly as written — it never generates one, and there is no per-framework setup, because there is nothing React-specific for Beaver to do at build time.

<Warning>
  A repository that is not a React app is refused before anything is built, with the framework it was detected as named in the message. A meta-framework that happens to depend on React — Next.js, Remix, Astro — is detected as that framework, not as React, and is refused. See [What counts as a React app](#what-counts-as-a-react-app).
</Warning>

## The contract

<Steps>
  <Step title="A Dockerfile">
    At the repository root, or at the path you configure. Beaver builds it as written and never generates one. It does detect your framework, but only to decide whether the app is one it deploys — never to change how it is built. See
    [Dockerfile requirements](/deploy/dockerfile-requirements).
  </Step>
  <Step title="A port">
    The port your app listens on, declared with `EXPOSE`. `beaver init` reads it and proposes it in `.beaver/config.yml`.
  </Step>
</Steps>

That is all Beaver requires beyond the app being React. The rest of this page is a checklist that makes the first deploy healthy.

## What counts as a React app

Beaver detects your framework from `package.json` before it builds, and deploys only what it recognizes as React.

| Your repository | Detected as | Deploys |
| --- | --- | --- |
| `react` + Vite, or any bundler you chose | `react` | Yes |
| `react-scripts` (Create React App) | `react` | Yes |
| React with no bundler, server-rendered by your own code | `react` | Yes |
| Next.js, Remix or Astro — even with `react` in `package.json` | `next`, `remix`, `astro` | No |
| Vue, Angular, Svelte, Nuxt, SvelteKit | that framework | No |
| A Node backend with no front-end framework (Express, NestJS, Fastify, Koa, Hapi, AdonisJS) | that framework, or `generic` | No |
| Go, Python, Ruby, Rust, the JVM | that language | No |
| Nothing recognizable | nothing | No |

The last row matters as much as the others: a repository Beaver cannot identify is refused rather than attempted. If you believe a React app is being misdetected, `beaver deploy` prints what it detected before it refuses.

## Checklist

- **Listen on `0.0.0.0`**, not `localhost` or `127.0.0.1`. A server bound to the loopback address cannot be reached from outside its container.
- **Read the port from `PORT`** and default to the port you `EXPOSE`, so the configured port and the real one cannot drift.
- **Answer a health path** with `200` and no database dependency, such as `/healthz`. Add a `HEALTHCHECK` and tell Beaver the path with `beaver config health --http /healthz` ([Health checks](/deploy/health-checks)).
- **Handle `SIGTERM`** and finish in-flight requests, so a rolling release drains instead of cutting connections.
- **Run as a non-root user** (`USER`), and write run-time files to a mounted volume, not the image.
- **Keep secrets out of the image.** Set them per environment with [Environment variables](/deploy/environment-variables). Add a `.dockerignore` for `.git`, `.env*` and local dependency folders.
- **Commit your lockfile** (`package-lock.json`, `yarn.lock` or `pnpm-lock.yaml`). The Builder clones the commit you pushed, so anything untracked is missing from the build.
- **Never put a secret in a client-side variable.** Bundlers inline `VITE_*` and `REACT_APP_*` values into the JavaScript they emit, so anything in one is public to every visitor. See [Environment variables](/deploy/environment-variables).

## Two starting shapes

Both shapes below are React apps; they differ only in what serves the built assets. They are illustrations to adapt, not drop-in files — your build command, output directory and Node version are yours.

<Tabs>
  <Tab title="Static build, served by nginx">
    The common shape. Build the bundle in one stage, serve the output with a web server on a non-privileged port. Port `8080`, health `/healthz`.

    ```dockerfile Dockerfile
    FROM node:22-alpine AS build
    WORKDIR /src
    COPY package.json package-lock.json ./
    RUN npm ci
    COPY . .
    # Public, build-time values are inlined here. Never pass a secret.
    ARG VITE_API_URL
    RUN npm run build

    FROM nginxinc/nginx-unprivileged:1.27-alpine
    # Needed for client-side routing: serve index.html for unknown paths,
    # and answer the health path without reaching the app.
    COPY nginx.conf /etc/nginx/conf.d/default.conf
    COPY --from=build /src/dist/ /usr/share/nginx/html/
    EXPOSE 8080
    HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
      CMD wget -qO- http://127.0.0.1:8080/healthz || exit 1
    ```

    The `nginx.conf` that makes a single-page app work, health path included:

    ```nginx nginx.conf
    server {
      listen 8080;
      root /usr/share/nginx/html;

      location = /healthz { return 200 "ok\n"; }

      location / { try_files $uri $uri/ /index.html; }
    }
    ```

    Create React App is identical bar the output directory: copy `/src/build/` instead of `/src/dist/`, and use `REACT_APP_*` for build-time values.
  </Tab>
  <Tab title="Served by a Node server">
    For a React app whose own server handles requests — an API on the same origin, or server-side rendering you wrote yourself. Port `3000`, health `/healthz`.

    ```dockerfile Dockerfile
    FROM node:22-alpine AS build
    WORKDIR /src
    COPY package.json package-lock.json ./
    RUN npm ci
    COPY . .
    RUN npm run build

    FROM node:22-alpine
    WORKDIR /app
    ENV NODE_ENV=production PORT=3000
    COPY package.json package-lock.json ./
    RUN npm ci --omit=dev
    COPY --from=build /src/dist/ ./dist/
    COPY server.js ./
    USER node
    EXPOSE 3000
    HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
      CMD wget -qO- "http://127.0.0.1:${PORT}/healthz" || exit 1
    CMD ["node", "server.js"]
    ```

    The server must bind `0.0.0.0` and read `PORT`, answer `/healthz` without touching a database, and serve `index.html` for unmatched paths so client-side routes survive a refresh.
  </Tab>
</Tabs>

## Deploy

<Tabs>
  <Tab title="Dashboard">
    Push the project to GitHub with the `Dockerfile` at the repository root. Choose **Deploy application**, pick the repository and branch, and deploy. See [Deploy from GitHub](/deploy/from-github).
  </Tab>
  <Tab title="Desktop">
    <Note>Desktop does not deploy. Open the project folder in Desktop to see its state, then deploy from the Dashboard or the CLI.</Note>
  </Tab>
  <Tab title="CLI">
    ```bash
    beaver init                                   # proposes .beaver/config.yml from your Dockerfile
    beaver config health --http /healthz
    git add -A && git commit -m "Add Beaver config" && git push
    beaver deploy --cloud paperclip-prod
    ```
    The command refuses to run with uncommitted changes or unpushed commits. See [Deploy from a local project](/deploy/from-local-project).
  </Tab>
</Tabs>

## Verify

Check the image locally before you deploy:

```bash
docker build -t myapp-check .
docker run --rm -p 8080:8080 myapp-check
curl -i http://localhost:8080/healthz      # 200
```

After the deploy, `beaver inspect` shows the release and its health, and `beaver preflight --full` rehearses a throwaway candidate: build, health, teardown.

## Common failures

| Symptom | Cause and fix |
| --- | --- |
| The release never becomes healthy and the old version keeps serving | The server is bound to `127.0.0.1`, or the health path returns a non-success status. See [Health checks](/deploy/health-checks) and [An unhealthy release](/operate/troubleshoot-deploy-unhealthy). |
| `502` or `503` after a successful deploy | The configured port is not the port the process listens on. Match `EXPOSE`, the code and `.beaver/config.yml`; see [502 or 503](/operate/troubleshoot-502-503). |
| The container exits immediately | The start command fails or the process daemonizes. Run the image locally with `docker run` and read its output; see [A failed build](/operate/troubleshoot-build). |
| The deploy is refused before any build, naming a framework | The repository was detected as something other than React. See [What counts as a React app](#what-counts-as-a-react-app). |
| A route works from the nav but `404`s on refresh or a direct link | The web server is not falling back to `index.html`. See the `nginx.conf` in the first shape above. |
| An API URL or key is `undefined` in the browser | The value was not present at build time. Bundlers inline these during `npm run build`, not at container start; pass it as a build argument, and never pass a secret. |
| The build fails on a dependency install | The lockfile is not committed. The Builder clones the commit you pushed; untracked files are missing. |
| The server reads the wrong address or port | Set `HOST`/`HOSTNAME`/`PORT` in the Dockerfile. See [Environment variables reference](/reference/environment-variables). |

## Production notes

- Behind Beaver's proxy, configure your app to trust proxy headers if it reads the client address, and use `X-Forwarded-*` rather than the socket address.
- Prefer small, pinned base images and multi-stage builds; they build faster and ship less. A static React app ships no Node runtime at all.
- Set long cache headers on the hashed asset filenames your bundler emits, and no-cache on `index.html`, so a release takes effect immediately without re-downloading unchanged assets.
- Keep databases and caches out of your app image: use a [hosted database](/data/bring-your-own-database) or a [separate container](/data/run-a-database-container).
