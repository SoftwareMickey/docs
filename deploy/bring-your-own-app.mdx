Beaver does not know or care what your app is written in. If it builds into a Docker image and listens on a port, it deploys — React or Rails, Go or COBOL.
There is no per-framework setup, because there is nothing framework-specific for Beaver to do.

## The contract

<Steps>
  <Step title="A Dockerfile">
    At the repository root, or at the path you configure. Beaver builds it as written; it never generates one and never detects your framework. See
    [Dockerfile requirements](/deploy/dockerfile-requirements).
  </Step>
  <Step title="A port">
    The port your app listens on, declared with `EXPOSE`. `beaver init` reads it and proposes it in `.beaver/config.yml`.
  </Step>
</Steps>

That is all Beaver requires. The rest of this page is a checklist that makes the first deploy healthy.

## Checklist

- **Listen on `0.0.0.0`**, not `localhost` or `127.0.0.1`. A server bound to the loopback address cannot be reached from outside its container.
- **Read the port from `PORT`** and default to the port you `EXPOSE`, so the configured port and the real one cannot drift.
- **Answer a health path** with `200` and no database dependency, such as `/healthz`. Add a `HEALTHCHECK` and tell Beaver the path with `beaver config health --http /healthz` ([Health checks](/deploy/health-checks)).
- **Handle `SIGTERM`** and finish in-flight requests, so a rolling release drains instead of cutting connections.
- **Run as a non-root user** (`USER`), and write run-time files to a mounted volume, not the image.
- **Keep secrets out of the image.** Set them per environment with [Environment variables](/deploy/environment-variables). Add a `.dockerignore` for `.git`, `.env*` and local dependency folders.
- **Commit your lockfiles** (`package-lock.json`, `go.sum`, `poetry.lock`, …). The Builder clones the commit you pushed, so anything untracked is missing from the build.

## Three starting shapes

These are the shapes real apps take. They are illustrations, not a list of supported frameworks — adapt the build stage to your stack. Each one is built and run in CI (last run 2026-10-02, Docker 29.1.3); the Dockerfiles below are exactly the ones tested.

<Tabs>
  <Tab title="Compiled binary">
    Build in one stage, ship only the binary. Port `8080`, health `/healthz`.

    ```dockerfile Dockerfile
    FROM golang:1.23-alpine AS build
    WORKDIR /src
    COPY go.mod ./
    COPY . .
    RUN CGO_ENABLED=0 go build -trimpath -ldflags="-s -w" -o /out/server .

    FROM alpine:3.20
    RUN adduser -D -u 10001 app
    COPY --from=build /out/server /usr/local/bin/server
    ENV PORT=8080
    USER app
    EXPOSE 8080
    HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
      CMD wget -qO- "http://127.0.0.1:${PORT}/healthz" || exit 1
    CMD ["server"]
    ```

    Any compiled language (Go, Rust, Java native image, .NET) follows this shape: a build stage, then a small runtime image holding the artifact.
  </Tab>
  <Tab title="Interpreted server">
    Install dependencies, copy the source, run it. Port `3000`, health `/healthz`.

    ```dockerfile Dockerfile
    FROM node:22-alpine
    WORKDIR /app
    ENV NODE_ENV=production PORT=3000
    COPY package.json ./
    # With dependencies, commit package-lock.json and use: RUN npm ci --omit=dev
    COPY server.js ./
    USER node
    EXPOSE 3000
    HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
      CMD wget -qO- "http://127.0.0.1:${PORT}/healthz" || exit 1
    CMD ["node", "server.js"]
    ```

    Python, Ruby, PHP, Node.js and the JVM follow this shape: a runtime base image, dependencies, then the start command.
  </Tab>
  <Tab title="Static site">
    Build the site in a first stage if it needs one, then serve the output with a web server on a non-privileged port. Port `8080`, health `/healthz`.

    ```dockerfile Dockerfile
    FROM nginxinc/nginx-unprivileged:1.27-alpine
    COPY nginx.conf /etc/nginx/conf.d/default.conf
    COPY site/ /usr/share/nginx/html/
    EXPOSE 8080
    HEALTHCHECK --interval=30s --timeout=3s --start-period=5s --retries=3 \
      CMD wget -qO- http://127.0.0.1:8080/healthz || exit 1
    ```

    Single-page apps, documentation sites and anything that builds to HTML, CSS and JavaScript. Front-end bundlers inline `VITE_*`-style variables at build time, so never put a secret in one.
  </Tab>
</Tabs>

## Deploy

<Tabs>
  <Tab title="Dashboard">
    Push the project to GitHub with the `Dockerfile` at the repository root. Choose **Deploy application**, pick the repository and branch, and deploy. See [Deploy from GitHub](/deploy/from-github).
  </Tab>
  <Tab title="Desktop">
    <Note>Desktop does not deploy. Open the project folder in Desktop to see its state, then deploy from the Dashboard or the CLI.</Note>
  </Tab>
  <Tab title="CLI">
    ```bash
    beaver init                                   # proposes .beaver/config.yml from your Dockerfile
    beaver config health --http /healthz
    git add -A && git commit -m "Add Beaver config" && git push
    beaver deploy --cloud paperclip-prod
    ```
    The command refuses to run with uncommitted changes or unpushed commits. See [Deploy from a local project](/deploy/from-local-project).
  </Tab>
</Tabs>

## Verify

Check the image locally before you deploy:

```bash
docker build -t myapp-check .
docker run --rm -p 8080:8080 myapp-check
curl -i http://localhost:8080/healthz      # 200
```

After the deploy, `beaver inspect` shows the release and its health, and `beaver preflight --full` rehearses a throwaway candidate: build, health, teardown.

## Common failures

| Symptom | Cause and fix |
| --- | --- |
| The release never becomes healthy and the old version keeps serving | The server is bound to `127.0.0.1`, or the health path returns a non-success status. See [Health checks](/deploy/health-checks) and [An unhealthy release](/operate/troubleshoot-deploy-unhealthy). |
| `502` or `503` after a successful deploy | The configured port is not the port the process listens on. Match `EXPOSE`, the code and `.beaver/config.yml`; see [502 or 503](/operate/troubleshoot-502-503). |
| The container exits immediately | The start command fails or the process daemonizes. Run the image locally with `docker run` and read its output; see [A failed build](/operate/troubleshoot-build). |
| `exec ... no such file or directory` | A binary built for a different libc or architecture than the runtime image. Build statically, or use matching base images. |
| The build fails on a dependency install | The lockfile is not committed. The Builder clones the commit you pushed; untracked files are missing. |
| A framework reads the wrong address or port | Set `HOST`/`HOSTNAME`/`PORT` in the Dockerfile. See [Environment variables reference](/reference/environment-variables). |

## Production notes

- Behind Beaver's proxy, configure your app to trust proxy headers if it reads the client address, and use `X-Forwarded-*` rather than the socket address.
- Prefer small, pinned base images and multi-stage builds; they build faster and ship less.
- Use a [managed service](/data/create-a-service) for databases and caches rather than running them in your app image.
